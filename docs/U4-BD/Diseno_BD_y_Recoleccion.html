De la pregunta a la base para análisis

Las variables e indicadores de tu pregunta se convierten en las columnas de tu base. Si no puedes ubicar una variable en este flujo, todavía no está lista para entrar a ella.

Important

En esta unidad respondemos: “¿qué estructura de datos necesito para contestar mi pregunta de investigación con evidencia verificable?”

Pasos para organizar nuestros datos

  1. Partir de la pregunta → ¿Qué debo observar para responder mi pregunta general y específicas?
  2. Diseñar estructura → ¿Una tabla (el punto de partida) o varias? ¿Qué campos necesito?
  3. Definir relaciones (si usas varias tablas) → ¿Cómo se conectan los datos entre sí?
  4. Establecer reglas → ¿Qué datos son válidos y cuáles no?
  5. Documentar todo → Crear un diccionario que explique cada variable.
  6. Planear recolección → ¿De dónde y cómo obtendré los datos?
  7. Transformar y preparar → Imputar, agregar y derivar variables según tu pregunta de investigación.
  8. Verificar calidad → ¿Cómo me aseguro de que los datos sean confiables?

De variables a organización de datos

  • Variable dependiente: lo que quiero explicar o predecir.
  • Variables independientes: los factores que pueden influir.
  • Variables derivadas: nuevas variables que calculo a partir de las anteriores.

Ejemplo (estudio de fraude en transacciones):

  • Variable dependiente: es_fraude (sí/no).
  • Variables independientes: monto, canal, tienda, cliente, fecha_hora.
  • Variables derivadas: hora_del_dia, dia_semana, monto_promedio_ultimo_mes.

¿Una tabla o múltiples tablas?

La respuesta depende de tu unidad de observación y de cómo llegaron los datos. Empieza con una sola tabla y divídela solo si hay una razón:

Formato plano (una sola tabla)

  • Cada fila es una observación completa
  • Encuestas, sensores o registros de una sola fuente
  • Dataset ya integrado desde el origen
  • La mayoría de repositorios públicos y Kaggle

Modelo relacional (múltiples tablas): cuando una tabla ya no basta

  • Datos de fuentes diferentes
  • Información que se repite en muchas filas (el cliente o la tienda de cada transacción)
  • Relaciones de muchos-a-muchos
  • Quieres que la base valide que cada transacción apunta a un cliente y una tienda que existen

Important

Aun si partes de varias tablas, el análisis estadístico requiere una sola tabla lista para analizar: la integrarás antes de analizar.

Conceptos clave para organizar datos

  • Identificador único: cada fila debe poder distinguirse de las demás con un código (p. ej., id_transaccion).
  • Tipos de datos y reglas de validación: números para cantidades, texto para nombres, fechas para tiempo; define qué valores son aceptables.
  • Identificadores estables, unidades y zona horaria: no cambies los códigos después y registra unidades (pesos, kg, %) y zona horaria en el diccionario.

Tipo de dato ≠ escala de medición (la escala determina qué análisis tienen sentido)

  • Nominal: categorías sin orden (canal: web, app).
  • Ordinal: categorías con orden (satisfacción: baja, media, alta).
  • Intervalo / razón: cantidades numéricas; solo en la razón el cero significa “ausencia” (monto).

Cuando una tabla no basta

PK (llave primaria): código único de cada fila. FK (llave foránea): apunta a la PK de otra tabla. Al separar clientes y tiendas, sus datos ya no se repiten.

¿Qué datos necesito?

  • Identifica todas las variables en tu diccionario.
  • Asegúrate que cada variable tenga una fuente definida.
  • Determina la frecuencia de recolección necesaria.

Métodos de recolección

  • Fuentes directas: encuestas que yo diseño, experimentos, observaciones.
  • Fuentes existentes: bases de datos públicas, APIs, archivos institucionales.
  • Herramientas de captura: formularios digitales, sensores, programas de descarga automática.

Muestreo: ¿a quién y cuántos casos?

  • Población: ¿a quién quiero generalizar? Marco muestral: ¿de qué lista puedo seleccionar realmente?
  • Una muestra es representativa si reproduce las características de la población relevantes para tu pregunta.
Tipo Técnica Cuándo usarla
Probabilístico (cada unidad tiene probabilidad conocida) Aleatorio simple, sistemático, estratificado, por conglomerados Si quieres inferir a la población y cuantificar el error
No probabilístico Por conveniencia, por cuotas, bola de nieve Estudios exploratorios o poblaciones de difícil acceso; sin inferencia estadística formal

¿Cuántos casos? Depende de la variabilidad y la precisión deseada; en pruebas de hipótesis, del tamaño del efecto y la potencia; en modelos predictivos, del desbalance de clases (p. ej., pocos fraudes entre muchas transacciones).

Warning

Si tu base ya existe (Kaggle, repositorios públicos), no elegiste la muestra: documenta cómo se obtuvo y qué población representa realmente.

Evaluación del origen de los datos

Antes de analizar, responde estas 6 preguntas de control:

Dimensión Preguntas clave
Procedencia ¿De dónde provienen los datos? ¿Quién los generó? ¿Son propios o de terceros?
Generación/recolección ¿Cómo se recolectaron? ¿Bajo qué condiciones? ¿Existe protocolo?
Estructura y alcance ¿Cuál es la unidad de observación? ¿Qué periodo cubren? ¿Qué cobertura geográfica/poblacional tienen?
Calidad y confiabilidad ¿Se validaron? ¿Hay faltantes, sesgos o errores conocidos? ¿Son consistentes entre periodos/fuentes?
Transformaciones previas ¿Son datos crudos o procesados? ¿Qué agregaciones/imputaciones se aplicaron? ¿Se integraron múltiples fuentes?
Restricciones y uso ¿Hay límites legales, éticos o de licencia? ¿El propósito original es compatible con tu proyecto?

Tip

Versión compacta: Procedencia · Generación · Estructura · Calidad · Transformaciones · Restricciones. Documenta respuestas breves en tu README.md o protocolo.

Important

Si no puedes responder con evidencia documental estas 6 dimensiones, tu base aún no está lista para análisis inferencial.

Control de calidad de los datos

La evaluación del origen responde qué preguntar antes de recolectar; el control de calidad responde cómo verificar lo que ya tienes.

Prevención (al capturar): formularios que validen automáticamente y listas de opciones cerradas.

Detección de errores (después de capturar)

  • Duplicados donde no deberían existir.
  • Valores fuera de rango y atípicos (outliers): investígalos antes de eliminarlos (¡el fraude es un atípico!).
  • Fechas lógicas; unidades, zonas horarias y categorías (web / Web) consistentes.

Documentación

  • Registra el origen y la fecha de captura de cada dato.
  • Originales intactos en una carpeta aparte; correcciones con scripts, no a mano.

Imputación: datos faltantes

Identifica primero por qué falta el dato (Little & Rubin, 2002; Rubin, 1976): MCAR (al azar, p. ej. error técnico), MAR (depende de otra variable observada) o MNAR (depende del valor mismo: modela la ausencia y haz análisis de sensibilidad). Los datos no distinguen MAR de MNAR: hace falta conocimiento del dominio.

Método Cuándo usarlo Limitación
Eliminar filas Pocos faltantes (<5%), MCAR Pierde información; sesga si no es MCAR
Media / mediana / moda Exploración rápida Subestima la varianza y distorsiona correlaciones
Valor anterior (fill) Series de tiempo, huecos cortos Sesga con huecos largos o tendencia
Regresión MAR, variables correlacionadas Subestima la incertidumbre
Imputación múltiple (Schafer & Graham, 2002; Sterne et al., 2009; van Buuren, 2018; van Buuren & Groothuis-Oudshoorn, 2011) MAR; análisis inferencial Más compleja de implementar y reportar

Warning

Documenta método y variables. Si tu proyecto es predictivo (ML), calcula la imputación solo con el conjunto de entrenamiento y aplícala al de prueba: imputar antes de dividir filtra información (data leakage).

Consideraciones éticas y de privacidad

  • Minimiza la recolección: solo recolecta lo que realmente necesitas.
  • Seudonimizar no es anonimizar: con códigos en vez de nombres, aún se puede reidentificar a alguien combinando edad, ciudad y ocupación.
  • Personas participantes: consentimiento informado y, cuando aplique, revisión de un comité de ética.
  • Controla el acceso y revisa licencias y términos de uso de datos de terceros.
  • Para compartir datos: enmascara, generaliza o usa datos sintéticos.

Note

Marco legal en México: particulares → Ley Federal de Protección de Datos Personales en Posesión de los Particulares (nueva ley, DOF 20/03/2025); entes públicos → ley general para sujetos obligados. Verifica la versión vigente y las políticas de tu institución.

Tres técnicas para proteger la privacidad

Técnica Qué hace Riesgo que queda
Seudonimización Reemplaza identificadores directos (nombre, CURP) por un código Si existe la tabla de equivalencias o hay cuasi-identificadores, se puede reidentificar
Enmascaramiento / generalización Agrupa o distorsiona valores (rangos de edad, región en vez de ciudad, ruido) Reduce el riesgo, no lo elimina; se pierde precisión
Datos sintéticos Se generan registros nuevos con un modelo (o reglas) ajustado a los datos reales Pueden filtrar información si el modelo memoriza registros reales; hay que evaluarlo

Los datos sintéticos son registros artificiales que buscan conservar patrones estadísticos de los datos reales sin que ninguna fila corresponda a una persona real.

Herramientas básicas

  • Python: Faker genera datos falsos aleatorios (útil para pruebas y demos, no preserva relaciones entre variables); SDV modela los datos reales para generar sintéticos.
  • R: synthpop y simPop.

Lista de buenas prácticas

Puntos clave para recordar

  • Planifica antes de recolectar: diseña tu estructura de datos antes de empezar a capturar información.
  • Documenta todo: mantén un diccionario actualizado de qué significa cada variable y qué transformaciones se le aplicaron.
  • Prepara, no solo recolecta: casi siempre necesitarás limpiar, imputar o agregar antes de analizar.
  • Empieza con una sola tabla: divídela solo si hay datos repetidos, varias fuentes o relaciones muchos-a-muchos.
  • Elige la granularidad correcta: la unidad de análisis (fila) debe corresponder con tu pregunta de investigación.
  • Considera la ética: protege la privacidad y recolecta solo lo necesario.

La calidad de tu análisis depende directamente de la calidad y preparación de tus datos.

Ejemplo práctico — Estructura en SQL

-- Primero las tablas que serán referenciadas
CREATE TABLE clientes (
  id_cliente TEXT PRIMARY KEY,
  segmento TEXT,
  fecha_registro DATE
);

CREATE TABLE tiendas (
  id_tienda TEXT PRIMARY KEY,
  categoria TEXT,
  ciudad TEXT
);

-- Tabla principal: cada fila es una transacción
CREATE TABLE transacciones (
  id_transaccion TEXT PRIMARY KEY,
  id_cliente TEXT NOT NULL REFERENCES clientes(id_cliente),
  id_tienda TEXT NOT NULL REFERENCES tiendas(id_tienda),
  fecha_hora TIMESTAMP NOT NULL,
  monto DECIMAL(10,2) NOT NULL CHECK (monto > 0),
  canal TEXT CHECK (canal IN ('pos','web','app','telefono')),
  es_fraude BOOLEAN NOT NULL DEFAULT 0
);

REFERENCES declara la llave foránea: la base rechaza transacciones de clientes o tiendas que no existen (en SQLite: PRAGMA foreign_keys = ON;). Solo un ejemplo; adáptalo a tu proyecto.

Datos sintéticos: usos y cuidados

¿Cuándo usarlos?

  • Compartir datos con colaboradores o publicarlos
  • Desarrollar y probar código o modelos sin exponer datos sensibles
  • Crear ejemplos educativos

Cuidados

  • Compara utilidad: ¿se conservan distribuciones y relaciones clave frente a los datos reales?
  • Evalúa privacidad: ¿hay filas casi idénticas a registros reales o casos raros reproducidos?
  • No son automáticamente libres de restricciones legales ni de licencia: consulta con quien custodia los datos originales

Herramientas recomendadas

  • Excel/Google Sheets: para empezar y datos pequeños.
  • SQLite: base de datos simple, ideal para aprender.
  • R/Python: para análisis más avanzados.
  • Google Forms: para recolectar datos con formularios.

Elige la herramienta según el tamaño de tus datos y tu experiencia.
